2.What happens when multiple security roles are assigned to a user? How is the level of security determined?
=>1.Start with Core Concept
2.Explain Behavior
3.State Rule
4.Give Example
5.Add Key Insight -Note

Example 
In D365, when multiple security roles are assigned to a user, the system follows a cumulative privilege model. This means privileges from all roles are combined, and the highest level of access is applied for each privilege.
For example, if one role gives User-level read access and another gives Business Unit-level access, the user will get Business Unit-level access.
There is no deny concept in D365 security; access is always additive and evaluated based on the most permissive level.

=> D365 CRM – OWNER TEAM vs ACCESS TEAM

OWNER TEAM
- Can own records ✅
- Has security roles ✅
- Access comes from role privileges
- Used for group ownership
- More permanent setup

ACCESS TEAM (Template-based)
- Cannot own records ❌
- No security roles ❌
- Gives record-level access only
- Access defined via template (Read, Write, etc.)
- Created automatically per record
- Used for collaboration (temporary access)

6. If in the production environment, you found an issue which will take 2 days to resolve which is on critical priority, but due to business requirement it should be resolved immediately. What would you do in that particular scenario?
Ans - 
First, I would analyze the impact and identify whether a temporary workaround can restore business operations. Since the issue is critical, my priority would be to minimize business downtime while simultaneously working on the permanent fix.
Since the issue was critical and directly impacting business operations, I first assessed whether there was a safe workaround to keep the business running. The root cause was a bug in the order transaction functionality where Quantity and Name values were not getting mapped correctly. The permanent fix required code changes, testing, and deployment, which would take approximately 2 days.

To minimize business impact, I coordinated with the business team and manually corrected the affected records in Production as a temporary workaround. This allowed critical transactions to continue without interruption. Simultaneously, I started working on the permanent fix in the development environment, performed testing, and followed the standard deployment process to move the fix to Production.

After deploying the permanent solution, I validated that new records were being processed correctly and ensured that all manually updated records were reconciled.
