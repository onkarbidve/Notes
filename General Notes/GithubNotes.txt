A Git conflict (merge conflict) happens when Git cannot automatically decide which change to keep because two people modified the same piece of code differently.

Example

Suppose the original file contains:

C#
string name = "Customer";

Show more lines
Developer A changes it to:
C#
string name = "Account";

Show more lines
Developer B changes it to:
C#
string name = "Contact";

Show more lines

When Developer A merges first, main becomes:

C#
string name = "Account";

`

Show more lines

Now Developer B tries to merge. Git sees:

Main branch says: "Account"
Developer B's branch says: "Contact"

Git doesn't know which one is correct, so it creates a conflict.

How a Conflict Looks

Git marks the conflicting section like this:

C#
<<<<<<< HEAD

string name = "Account";

=======

string name = "Contact";

>>>>>>> feature-branch

Show more lines

Meaning:

<<<<<<< HEAD = current branch (main)
======= = separator
>>>>>>> feature-branch = incoming changes
Resolving the Conflict

A developer manually decides what should remain.

Keep Account:

C#
string name = "Account";

Show more lines

Keep Contact:

C#
string name = "Contact";

Show more lines

Or combine both:

C#
string displayName = "Account Contact";

Show more lines

Then commit the resolution:

Shell
git add .

git commit -m "Resolved merge conflict"

Show more lines
Real D365 CRM Example

Imagine two developers are editing the same JavaScript file:

Developer A

JavaScript
formContext.getAttribute("name").setRequiredLevel("required");

Show more lines

Developer B

JavaScript
formContext.getAttribute("name").setRequiredLevel("none");

Show more lines

When merging, Git can't determine whether the field should be required or not.

A conflict occurs and the team must decide the correct business requirement.

When Conflicts Usually Occur
Two developers modify the same file and same lines.
One developer deletes a file while another edits it.
A branch is old and hasn't been synced with main for a long time.
How to Reduce Conflicts

✅ Pull latest changes regularly

Shell
git pull origin main

Show more lines

✅ Create small feature branches

✅ Merge frequently

✅ Communicate with team members when working on the same files

✅ Review incoming changes using Fetch before merging

Simple Analogy

Imagine two people editing the same sentence in a Word document:

Original:

"Customer Name"

Person A changes it to:

"Account Name"

Person B changes it to:

"Contact Name"

When combining the documents, someone must decide which text is correct. That's exactly what a Git conflict is

Git Notes 
==========
git init
 Creates a new Git repository by creating a hidden .git folder in the current directory.

git add .
 Stages all new, modified, and deleted files for the next commit.

git commit -m "Initial commit"
 Creates a commit (snapshot) of all staged changes.

git branch -M main
 Renames the current branch to main.

git remote add origin https://github.com/onkarbidve/Notes.git
 Connects the local repository to the GitHub repository.

git remote -v
 Displays the fetch and push URLs configured for the repository.

git push -u origin main
 Pushes code to GitHub and sets the upstream branch. Fails if remote already contains unrelated commits.

git push -u origin main --force
 Forcefully replaces the GitHub repository content with local content.

git status
 Shows modified, staged, untracked, and deleted files.

git branch
 Displays the current branch.

git log --oneline
 Shows commit history in a compact format.

git ls-remote origin
 Displays branches and commit hashes available in the remote repository.

git rm --cached <file>
 Removes a file from Git tracking but keeps it on disk.

rm -rf .git
 Completely removes Git history and repository configuration. Useful when starting fresh.

git show <commit-id>
 Displays details of a specific commit and files included in it.

git ls-files
 Lists all files currently tracked by Git.

git ls-files --stage
 Lists tracked files with modes such as:

100644 = normal file
160000 = submodule

find . -type f | grep -i "connection"
 Searches for files containing "connection" in the filename.

git grep -n "ClientSecret"
 Searches all tracked files for ClientSecret.

git grep -n "Secret"
 Searches all tracked files for the word Secret.

GitHub Push Protection Error:

GH013: Push cannot contain secrets


Means GitHub detected credentials such as:

Azure Client Secret
Connection String Secrets
API Keys
Tokens

Secret removal approach:

Remove secret value.
Commit again.
Push.
If secret exists in history, recreate Git history using rm -rf .git.

Why deleting the file later did not work:

GitHub scans all commits being pushed.
Secret existed in the initial commit history.

Why .git was created:

Running git init creates a hidden .git folder.
.git stores commits, branches, remotes, and configuration.

Why "embedded git repository" warning appeared:

warning: adding embedded git repository


Means a folder already contained its own .git directory.

Example structure:

NotesofD365&CRM
├── .git
├── General Notes
│   └── .git
├── Javascript Notes
│   └── .git
└── Notepad Notes
    └── .git


create mode 160000 General Notes

Indicates Git added the folder as a submodule, not as a normal folder.

To convert submodule to a normal folder:

rm -rf "General Notes/.git"
rm -rf "Javascript Notes/.git"
rm -rf "Notepad Notes/.git"


Remove submodule references:

git rm --cached "General Notes"
git rm --cached "Javascript Notes"
git rm --cached "Notepad Notes"


Add them back as normal folders:

git add .
git commit -m "Convert submodules to folders"
git push origin main
