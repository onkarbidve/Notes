Case → Quote → Book Job / Book Inspection → Work Order → Resource Booking.

1.determining the avilaibility based on the number of hours the technician has worked for a day 2. Determining the availaibility based on the holidays and existing booking 3. Companies based sorting of a technician

From a business perspective, this solution reduced manual scheduling effort, prevented technician overbooking, improved assignment accuracy, and provided users with real‑time visibility when booking jobs.

Business requirement -
Track how an asset loses value over time, and automatically record that reduction every financial year until it reaches its minimum (residual value) or its useful life ends.
Purchase Cost
Initial value of the asset when bought
Example: ₹100,000
Depreciation Method (WDV / Declining Balance)
Business chooses a method where:
Depreciation is calculated every year on the remaining (reduced) value of the asset
Depreciation Rate
Fixed percentage applied annually
Example: 20% per year
Residual Value (Salvage Value)
Minimum value the asset should reach
Example: ₹10,000
Once asset value reaches this, depreciation stops.
In one of my scenarios, the business wanted to track asset depreciation using the declining balance method within Dynamics 365 Field Service. They needed automatic yearly depreciation calculations based on asset value, financial year, and residual value
rate in %
Depreciation = 100,000 × 20% = 20,000 
New Value = 100,000 - 20,000 = 80,000
Depreciation = Current Asset Value × Depreciation Rate
New Value = Current Value - Depreciation
In real projects, depreciation is usually calculated using scheduled processes, but real-time calculation is useful for on-demand scenarios. For example, when a technician or manager needs to decide whether to repair or replace an asset, they need the latest asset value instantly.
The business requirement was to track how an asset depreciates over time using the declining balance (WDV) method within Dynamics 365 Field Service. The system needed to calculate depreciation annually based on the current asset value until it reaches the defined residual value or the end of its useful life.
The calculation followed:
Depreciation = Current Asset Value × Depreciation Rate
New Value = Current Value − Depreciation
The solution was implemented using Dynamics 365 Field Service (Dataverse) by extending the Customer Asset entity with custom fields such as Purchase Cost, Current Value, Depreciation Rate (%), Residual Value, and Last Depreciation Date. A Ribbon customization using Ribbon Workbench added a “Calculate Depreciation” button on the asset form, enabling users to trigger the calculation on demand. JavaScript was used to invoke a Custom Action, passing parameters like Asset ID and current values.
The core business logic was implemented in a C# Plugin registered on the Custom Action, ensuring centralized and controlled execution. The plugin calculated depreciation using the declining balance method by always applying the percentage on the latest current value. It included validations to ensure that the calculated value never dropped below the residual value, and if the computed value was less than or equal to the residual value, the plugin capped the value at the residual threshold and stopped further depreciation. The plugin then updated the asset record with the new depreciated value and maintained consistency of financial data. This approach ensured accurate calculation, enforcement of business rules at the server level, and reusability of the logic across different execution points such as manual trigger and future automation.

Field service plugin scenario 3:
Compliance based record creation 
The business requirement was to automate compliance management within the Field Service process. The organization needed technicians to complete compliance-related checklist questions before completing a booking. These compliance requirements could vary based on the Incident Type, Asset, or Functional Location associated with the service request.

The end-to-end process was:
A Case (service requirement) is created.
A Quote is generated.
A technician is scheduled based on availability, characteristics, and category matching the Incident Type requirements.
A Work Order is created after scheduling.
Based on the Work Order's Incident Type, Asset, and Functional Location, the applicable compliance records are identified.
Compliance checklist questions are automatically generated and linked to the Work Order for technician completion.

To meet this requirement, I designed and implemented a plugin-based solution in Dynamics 365. The solution used Many-to-Many relationships between Compliance and Incident Type, Asset, and Functional Location entities. Each Compliance record contained a set of checklist questions that acted as templates.

The plugin implementation included the following business rules:
Automatically generated Work Order checklist questions based on compliances associated with the Incident Type, Asset, and Functional Location.
Prevented duplicate questions from being created. If the same question was associated through multiple compliance sources (Incident Type, Asset, or Functional Location), only a single checklist question record was created on the Work Order.
Enforced mandatory questions by inheriting the mandatory configuration from the Compliance Question template.
Dynamically synchronized checklist questions whenever the Incident Type, Asset, or Functional Location on the Work Order was modified. Existing questions were recalculated, obsolete questions were removed, and new applicable questions were generated.

From a technical perspective:
Implemented FetchXML queries to retrieve Compliance records linked through Many-to-Many relationships.
Used the intersect='true' property in FetchXML to query the intermediary relationship tables.
Leveraged the distinct='true' (unique record retrieval) capability in FetchXML along with plugin validation logic to eliminate duplicate questions when the same compliance question was linked through multiple sources.
Designed the plugin to consolidate compliance records from Incident Type, Asset, and Functional Location before generating checklist questions.

Critical Part – Security Challenge

“The main challenge here is that webhook endpoints are public and can be abused.”
“Anyone can send a fake HTTP request to our endpoint and mark a payment as successful.”
signature generated using the payload and secret HMAC SHA256
Signature is not a unique identifier. It is a cryptographic hash used to verify authenticity and integrity of data.

HMAC-SHA256 cryptographic signature - razorpay_payment_id and secret to create the signature
why create the signature and check with razorpay if it is security how http endpoint is abused tell me as a beginnerThink of Razorpay like a secure bank, and your website's backend server like a digital warehouse.If you do not create and check that cryptographic signature, a malicious user (hacker) can trick your server into giving away digital products, courses, or services for free.Here is exactly how an attacker abuses a standard HTTP endpoint if you skip the signature check.The Cheat: How an Endpoint Gets AbusedImagine you have an online store selling an e-book for ₹500. Your backend server has a public HTTP endpoint waiting to receive success messages, like: https://yourwebsite.com.Scenario A: The Honest FlowA good user goes to your checkout page.They pay Razorpay ₹500.Razorpay tells your frontend, "Hey, they paid! Here is the order_id and payment_id."Your frontend sends those details to your payment-success HTTP endpoint.Your server verifies the signature, sees it is genuine, and sends the e-book.Scenario B: The Hacker Abuse (Without Signature Checks)A hacker opens your checkout page.Instead of paying, the hacker cancels the payment or closes the window.The hacker uses a basic, free tool (like Postman or a browser extension) to send a fake HTTP request directly to your public endpoint:URL: https://yourwebsite.comData Sent: {"order_id": "order_123", "payment_id": "pay_fake999"}The Vulnerability: If your server only checks if a payment_id exists in the request, it will blindly trust this fake data.The Result: Your server marks the fake order as "Paid" and sends the hacker the e-book for free.Why the Cryptographic Signature Stops the HackerTo prevent this abuse, Razorpay introduces a secret code blueprint that only your backend server and Razorpay's servers know: your Key Secret. The hacker does not know this secret code.When Razorpay processes a real payment, it hashes the text "order_id|payment_id" using that Secret Key to create the unique razorpay_signature.When the hacker tries to send fake data to your endpoint, they have to guess what the signature should be.The hacker sends fake data: {"order_id": "order_123", "payment_id": "pay_fake999", "razorpay_signature": "random_guess_123"}Your server takes the fake order_id and payment_id, links them together (order_123|pay_fake999), and mathematically mixes them with your actual private Key Secret.Your server calculates the real expected signature. Let's say it should mathematically be abcde789.Your server compares its calculation (abcde789) with the hacker's guess (random_guess_123).The Match Fails: Your server instantly knows someone is lying, rejects the request, and denies the hacker access.Without that signature verification, an HTTP endpoint is just an unprotected open door where anyone can text you "I paid" and your system will believe them.

Part A — Order Product Document Generation (Ceremony Booking Template)

1. Business Context Each order product/ceremony type has its own predefined Word template (e.g., a ceremony booking form with named boxes/sections per ceremony). Staff needed a way to generate a filled document per order on demand — pulling the correct template for each product on the order and populating it with that order's specific product/ceremony details — instead of manually opening the right template and typing values into each box by hand.

2. Requirement On clicking a Generate button on selecting event , the system should: fetch the Word template associated with each product on that event ,map each order product's data to the correct named box/placeholder in its template, fill it in, and return the completed document — without the user leaving the order form or handling any template manually.

3. Flow

User clicks "Generate" after selecting event
      │	
      ▼
JavaScript (ribbon button) → Azure Function (HTTP-triggered)
      │  1. Retrieve the order's line items (order products)
      │  2. For each product, fetch its associated Word template
      │     (stored as an attachment on the Product/related activity record)
      │  3. Map each product's fields to the named ceremony box in that template
      │  4. Fill the template (OpenXML — locate each named box, insert the mapped value)
      ▼
Filled document returned / attached back to the order

4. Architecture Ribbon/JavaScript button on the Order form → HTTP-triggered Azure Function → ServiceClient to retrieve order products and each product's linked template attachment → DocumentFormat.OpenXml to locate named content controls/bookmarks ("ceremony boxes") per template and fill them per-product → completed document attached back to the order (Note) or returned for download.

5. Why a Function

Not a plugin: template lookup (per product), OpenXML manipulation of named boxes across a variable number of line items, and returning a generated file to the user synchronously on a button click are outside what a sandboxed plugin should be doing — this is presentation-layer, on-demand generation work, not a Dataverse save-time rule.

Not Power Automate, for real client-driven reasons, not just preference:
No SharePoint dependency — PA's "Populate a Word template" action requires the template in SharePoint/OneDrive; here, templates are stored per-Product as CRM attachments, and the mapping is dynamic per order (which products, how many, which template each maps to) — not a single fixed template PA's action is built around.

Per-product, per-box mapping logic — each product's template has different named boxes; the mapping from "this order product" to "this specific box in this specific template" is conditional, data-driven logic, not a flat field-to-placeholder substitution PA's template action supports.
CI/CD & code review — customer-facing documents often must go through git-based review/testing; a Flow isn't unit-testable and doesn't fit that pipeline.
Synchronous, on-demand trigger (button click), not event-driven — the user needs the generated document back in the same interaction, which fits an HTTP-triggered Function called directly from the form's JavaScript, not an async webhook/event flow.

## Part B — Nightly Currency Exchange Rate Sync

**1. Business Context**
Dataverse's transactioncurrency.exchangerate field was updated manually/infrequently, causing stale conversions across every order, invoice, and report touching a non-base currency.

**2. Requirement**
Daily, fetch current rates for every active currency vs. base currency, update `exchangerate` on each record automatically.

**3. Flow**

Timer (daily) → RetrieveMultiple all active Currency records
  → one external API call for all rates → match by ISO code
  → batched update (ExecuteMultipleRequest) → log summary

**4. Architecture**
Timer-triggered Function, `ServiceClient` bulk read, one external rate call per run, `ExecuteMultipleRequest` batch write, Polly retry+jitter on the single call.

**5. Why a Function — honest version**
- **Close call, not decisive.** Currency list is small (a few dozen); a PA Flow (Recurrence → HTTP → loop → Update) could do this too.
- **Real justification is governance, not technical necessity:** this feed is foundational — every order/invoice/report depends on it being correct, so a client with engineering maturity wants it under source control, code review, and unit tests, given the downstream blast radius of it being wrong.

Invoice generation  - Azure functions

1. Real Estate Property Management Invoice Generation Scenario

I'll explain one scenario I worked on around automated invoice generation and digital signing for a real estate property management company using Azure Functions.

The client managed thousands of residential apartments and commercial properties across multiple locations. Every month, tenants had to be invoiced for rent, maintenance charges, parking fees, utility charges, clubhouse fees, and other recurring costs. Since the company managed approximately 30,000 properties, generating invoices manually was not feasible. The client wanted a fully automated solution that could generate, digitally sign, store, and track invoices at the end of each billing cycle.

The end-to-end business process was:

Property Lease
Monthly Charges Calculation
Invoice Generation
Digital Signing
Storage
Tenant Notification

At the end of every month, a Timer Trigger Azure Function executed automatically. The function retrieved all active tenant records from Dataverse that required invoicing. Since the number of records was large, Dataverse paging was implemented to fetch all invoice-eligible records across multiple pages.

After collecting the tenant data, the Azure Function retrieved the organization's digital signing certificate from Azure Key Vault using Managed Identity authentication. The certificate was loaded only once and reused throughout the batch process to reduce Key Vault calls and improve performance.

The system then began invoice processing using controlled parallelism with Parallel.ForEachAsync. For each tenant, the system calculated monthly rent, maintenance fees, parking charges, utility charges, late payment penalties, and applicable taxes. A PDF invoice was generated containing all billing details and then digitally signed using the certificate from Key Vault.

Once signed, the invoice was uploaded to Azure Blob Storage and the corresponding Dataverse records were updated with invoice status, generation date, invoice number, and document location.

To ensure reliability, every invoice was processed independently inside a try-catch block. If invoice generation failed for a specific tenant due to missing lease data or calculation issues, that tenant record was flagged for manual review while the remaining invoices continued processing without interruption.
As part of the optimization effort, I implemented Dataverse paging, certificate reuse, configurable concurrency controls, reusable service components, and centralized logging. This significantly reduced invoice processing time and improved maintainability.

From a business perspective, the solution eliminated manual invoice generation, reduced billing errors, improved regulatory compliance through digital signatures, and ensured that all tenant invoices were generated within the required billing window.

PCF- Powerapps componenet framework 

Recently, I worked on two PCF proof-of-concepts. The first was a custom International Phone Number control for a Model-Driven App. The requirement was to capture phone numbers with country codes in a single field. I developed a field-type PCF using TypeScript, HTML, and CSS, where users could select a country code and enter the phone number. I handled data binding through getOutputs(), rendering through updateView(), and customized the UI to improve the user experience compared to the standard textbox.

The second was a Dataset PCF for Opportunities. Instead of displaying opportunities in a standard grid, I built a card-based view that displayed Opportunity Topic and Estimated Revenue in a more visual format. I used Dataset APIs such as context.parameters.dataset, sortedRecordIds, records[id], and getFormattedValue() to retrieve records and dynamically generate the UI. I also implemented click functionality to navigate users directly to the Opportunity record from the card.

Through these implementations, I gained hands-on experience with PCF lifecycle methods (init, updateView, getOutputs, destroy), manifest configuration, dataset controls, event handling, custom styling, deployment using Power Platform CLI, and integrating PCFs into Model-Driven Apps.

The standard controls did not provide the desired user experience. PCF allowed us to create a customized UI while still leveraging Dataverse data and Model-Driven App capabilities. It helped improve usability without changing the underlying data model.

If the interviewer asks "Field PCF vs Dataset PCF?"

You can answer:

For the phone control, I used a Field PCF because it worked on a single Dataverse column. For the Opportunity card view, I used a Dataset PCF because it needed to render multiple records from a view and provide a custom presentation layer.

Plugins 

1.Prevalidation 
- Data validation before security checks 
- Outside the database transaction 

1. A plugin in PreValidation runs before the platform's security validation, but the operation will still undergo security checks later in the pipeline. The plugin does not bypass security. The benefit is that your validation logic can execute before Dataverse spends effort on the standard security and transaction processing
2.Earliest stage, best for validation and cancellation of operations before Dataverse performs security and transactional processing.
3.PreValidation runs before security checks and before the database transaction starts. Because it is outside the transaction, we can perform validation and reject invalid requests early, avoiding the overhead of creating a transaction and rolling it back later.
4.Security checks 
PreValidation executes before Dataverse performs its security checks. This allows business validations to run first and reject invalid requests early. If the plugin throws an exception in PreValidation, the request is stopped before Dataverse spends resources on security validation and transaction processing.

Example - 
1. Prevent record deletion based on its associated accounts - counter-> refrential restrict relationship - For simple parent-child deletion prevention, I would use Referential Restrict. I would choose a PreValidation plugin only when the business rule cannot be achieved through relationship behaviour .
Plugin here can be used for restricting the record based on specific record status like active.
2.PreValidation plugin on the Order products Update message. The plugin checked whether the order status was Closed or Fulfilled. If a business user attempted to modify restricted fields after closure, the plugin threw an exception. Since PreValidation executes before security checks and before the database transaction starts, the invalid update was rejected early, reducing unnecessary processing.
In an ERP-integrated environment, we used PreValidation to prevent updates to invoices belonging to closed accounting periods. This ensured financial compliance while avoiding unnecessary transaction processing.
